# Sources and collection

[Documentation index](../README.md). Current reference; dated repair evidence lives in [History](history.md).

## Sources

**Gmail and Calendar through a token broker.** Instead of `gog`, a Gmail or Calendar account can use `"transport": "broker"`: a service you run (a hosted control plane, say) keeps the Google OAuth client and its secret, and this machine keeps the account's refresh token (`mail_grants.py`: `mail-grants.json` next to the database, mode 600, sealed with the message key). Set `google_broker.url` and put this machine's token in the `google-broker` credential. For each call, `google_api.py` asks the broker for a short-lived access token for that one account and scope, sending the refresh token along, then calls Google's REST API directly. The broker answers `POST {"email", "scope", "refresh_token"}` with `{"access_token", "expires_in", "scopes"}` and keeps neither token (an account connected before this asks without `refresh_token` until its sign-in is moved here), `POST {"email"}` with the granted `scopes`, and 403 for a scope the owner didn't grant. Only a fixed list of Gmail and Calendar methods can be called; anything else is refused before a token is asked for. Sending and snoozing work only when the owner granted `gmail.send` or `gmail.modify` at the broker, as with `gog`. The hosted control-plane broker currently grants read-only plus optional send, not `gmail.modify`; thread snoozing therefore needs another already-granted supported route.

**Outlook and Outlook Calendar (Microsoft 365 and Outlook.com).** `ms_graph.py` reads them through Microsoft Graph with delegated scopes only: `User.Read`, `Mail.Read` and `Calendars.Read`, plus `Mail.ReadWrite` and `Mail.Send` when you turn sending on. Two transports: `"broker"` works like the Google broker (`microsoft_broker.url`, the `microsoft-broker` credential, the same protocol with Graph scope names; the refresh token Microsoft rotates comes back as `refresh_token` and replaces the kept one), and `"graph"` uses your own Entra app registration (`microsoft_graph.client_id`, `tenant`, public client flows on), a device-code sign-in, and a refresh token in a mode 600 credential file per account. Outlook mail is stored like Gmail, so cards, replies, sending and snoozing work the same: a reply goes out as the exact message (threading headers kept), snoozing moves the thread's Inbox messages to a `Snoozed` folder and back, unread, unless someone already replied. Graph has no signature API, so the signature is the one your recent sent mail ends with (found when at least three share it), or the one you set in Settings, Signatures. There each mailbox has one card with a small editor (bold, italic, underline, link, image by address, text colour, clear, and the HTML itself); with nothing set, it imports the mailbox's own first: Gmail's signature (read with `gmail.readonly`, the scope the send check already uses) or the one Outlook's sent mail ends with. **Use mailbox signature** drops yours. What you save is cleaned to plain formatting, links and images. Preparations save email attachments (Gmail and Outlook) with `assistant attachment`; with message protection on they are kept encrypted ([configuration](configuration.md#message-protection)). Shared calendars sync by delta like the main one. Not matched: messages deleted for good rather than moved to Deleted Items. Right after you connect, Microsoft can refuse the new sign-in for a few minutes while it takes the permissions: a broker account whose `connected_at` is less than 15 minutes old retries with backoff (`microsoft_signin_pending`), and a broker that answers 503 or 429 is asked again after its `Retry-After` (`microsoft_broker_busy`). Later refusals show `microsoft_signin_expired` and retry hourly, or as soon as you connect the account again.

Collectors read existing source content. The optional Salesflare `join_pipelines` setting also adds your own user to matching CRM accounts; it is empty by default. Each collector runs in its own thread with its own checkpoint, so a slow or failing source never blocks the others. Absence from a later read is never treated as deletion.

Add a plugin account with `assistant connect github` (or `stripe`, `intercom`, `x`, `linkedin`, `trello`, `rss`): it asks for the fields that connector needs. The dashboard does the same under Connections, **+ Add** (see [Usage](usage.md)). You can also add accounts to `config.json` by hand, using the keys above (each connector's header has a full example), and restart the service.

- **Gmail:** follows Gmail history after a seven-day import; replays the retained window when history expires. Replies keep their new text whole and only 3,000 characters of quoted history. Sending approved drafts and snoozing threads use separate workers and only scopes already granted.
- **Outlook:** the same as Gmail, following changed messages after a seven-day import.
- **Calendar:** seven past and thirty future days, recurring events expanded, incremental sync token with a daily full refresh. A missing event is "unavailable", not "cancelled". Context for email and preparation, not a reminder feed.
- **Slack:** conversations you already belong to; never joins channels or opens DMs. Per-conversation cursors, overlap rereads for edits, deferred retries for failed thread pages, and provider `Retry-After` honoured across restarts (plus a random extra wait, so computers sharing a connection don't retry together). Slack allows apps outside its Marketplace about one history or thread read a minute per workspace, and a Maton connection gets no more than that, shared by everything on the same connection: this collector, another computer running The Machine for the same account, and your own scheduled posts that check a channel first. So the collector spends at most one such read every `slack_read_seconds` and leaves the rest. It reads busy conversations within the hour and quiet ones once a day, and reads a direct message only when Slack says it has a new message. Posting isn't held back by this: a send Slack refuses as rate limited waits and goes out a few minutes later. The first import reads where the activity is: a quick look at every conversation (a call outside that limit) shows when a direct message last had a message and when you last read each channel, so conversations active today get their last 24 hours read first, then the rest of the week, and quiet ones come last. A direct message with nothing in the window isn't read at all. Signals start within minutes; the whole first import of a large workspace still takes hours. Don't connect the same Slack account on two computers if you can avoid it; they share that one read a minute.
- **Salesflare CRM:** only colleagues' emails that don't involve you (yours come from Gmail) and meetings with notes. With `join_pipelines`, it adds your own user to accounts linked to opportunities in those pipelines (a POST, never another user).
- **Android:** the plugin peeks OpenClaw's event queue for notifications from your phone node, with periodic direct reads to catch gaps. Repeated updates merge into one episode; one-time codes are omitted. Not a complete history.
- **WhatsApp:** reads your existing `wacli` store (`auth status`, `messages list` only, always `--read-only`), rereading the last seven days. New messages arrive through the `wacli sync` that `assistant connect whatsapp` sets up (or your own).
- **OpenClaw Gateway:** failed agent runs on Telegram, refused hand-offs and failed Telegram sends, grouped per half hour with secrets redacted. The first Gateway source also carries **The Machine's own errors** (`machine.fault`): see [The Machine fixes itself](../README.md#the-machine-fixes-itself).
- **GitHub:** notifications on threads you take part in (review requests, mentions, assignments, comments, threads you opened), each with the issue or PR and its latest comment. GET requests only; nothing is marked read. Each run checks that `gh` is logged in as `login`. Optional failed workflow runs per repository.
- **Stripe:** only events worth a look are stored: failed payments, disputes, ended subscriptions, scheduled cancellations, past due or unpaid, and new subscriptions of at least `large_subscription_monthly` a month. GET on the account, events and customers only; it never refunds, retries or changes anything. Each run checks the key belongs to `stripe_account`. For a direct key, create a restricted key with read access to Events, Customers and Account.
- **Intercom:** conversations updated in the last seven days (`bootstrap_days`), read in frozen search windows whose cursor commits with the conversations. Polls overlap six hours, the whole window is reread daily, and an expired cursor replays its window. REST with API version 2.11, and only `GET /me`, `GET /conversations/<id>` and the conversation search (a read-only POST); anything else is refused before the token is read, so it never replies, assigns, closes, tags or sends. Connecting reads the workspace from the token on `GET /me` and keeps its ID and name, the admin and the region (US, EU or Australia); every sync checks the workspace and admin again, exactly. A token from another workspace can't replace an account's own: add it as another account. Intercom returns at most 500 parts per conversation. The opening message keeps up to 20,000 characters and the latest history fills the rest of a 40,000-character body; anything cut is flagged. Attachments aren't collected. Get the token in Intercom's Developer Hub: your app, Authentication; read permissions are enough.
- **LinkedIn:** inbox conversations and messages (`connectors/linkedin.py` with `integrations/linkedin_inbox.py`), read through LinkedIn's own messaging API from a tab parked on `linkedin.com/robots.txt`, so nothing is marked read. Hourly in waking hours only (`poll_seconds`, `active_hours`), to keep automated LinkedIn traffic low. Pages follow LinkedIn's own cursors and commit with the messages; an unfinished scan continues after 30 seconds and keeps its lower bound through outages, however long; only a completed scan advances it. Spam is skipped. A busy browser retries in 10 minutes, signed out hourly, and setup and doctor say in plain words that LinkedIn is signed out in that browser. Every tab the reader opens is closed when it's done, also tabs a stopped run left behind; a sign-in tab you opened yourself stays. LinkedIn's query IDs are pinned; `linkedin_inbox.py discover` refreshes them when LinkedIn changes its client. A browser holds one LinkedIn sign-in, so a second LinkedIn account gets a browser profile of its own (`"browser_profile"`, and `"browser_cdp"` when read directly, on the account); it reads and sends there. No API key needed.
- **X:** replies, mentions and the DM inbox for each X account signed in to the OpenClaw browser (`connectors/x.py` with `integrations/x_inbox.py`), read through the owner's own signed-in x.com session (the same requests x.com makes, not X's developer API) from a background tab, so nothing is marked seen. Several accounts can share the browser through X's account switcher: x-inbox switches to the one it reads and always back to `primary`, one run at a time, and only while no other job holds the browser lease. An account can also have a browser profile of its own (`"browser_profile"`, and `"browser_cdp"` when read directly, on the account): it reads and sends there. Poll it hourly or less often (`poll_seconds`, default waking hours 07:00–23:00 via `active_hours`): X is sensitive to frequent automated reads. Encrypted X Chat isn't read. As with LinkedIn, a signed-out browser gets a plain-language hint and the reader closes the tabs it opened. No API key needed. Replies and DMs can be sent too, only after your approval (see [message actions](usage.md#message-actions)).
- **Watching it work:** while a Do it run is on the browser, its Preparing card shows that tab live: a small picture every few seconds, right of its steps (below them on a phone), larger on a click, gone when the run moves on. It is only ever a tab that task opened itself (by the target ID its own `open` step answered with): that run's, or one an earlier run of the same task left open and this run carries on in (after a sign-in, a retry or a Change), in the browser `browser_cdp_url` points at (127.0.0.1 only); never another task's tab or yours. It is taken over DevTools without bringing anything to the front: a tab in the background shows no new picture until the run brings it forward. The pictures stay in the service's memory for a few seconds, only for the dashboard, and are never logged or saved.
- **When a task waits on the browser:** a card whose Do it run has been in the browser for 45 seconds or more, or that stopped right after a browser step to ask for help (a sign-in, a captcha, a code), shows **Open the browser**. It brings the tab that task uses to the front on the computer the browser runs on, and with `browser_url` (or `browser_vnc`) it also opens that viewer (on Telegram too, when it is an https page).
- **View in browser:** a ready card whose Do it run worked on a page in the assistant's browser (filled in a form, prepared something to submit, pay or book) gets **View in browser**. It brings that task's own tab to the front there, as the run left it, or opens the page again there when the tab is gone, and opens the viewer (`browser_url` or `browser_vnc`), so you check and submit with the run's sign-in and entries, not in your own browser. A link the run added to the same site works the same way. On Telegram it opens the dashboard, which does the same. The card never carries the page's address; other links lose token-like query values.
- **When a task waits on your sign-in:** a Do it run that hands a sign-in to you (a password, a code, a passkey: its blocker says so, and it keeps that tab open) shows **Waiting for you to sign in** with a **Sign in** button on the card. On Telegram the card gets the same button and a **Needs you to sign in** notification (and phone push); both open the dashboard's sign-in dialog for that task (`#signin-for=<task id>`, needs `dashboard_host`). Signing in through the dialog carries the task on by itself, the same as **Continue**. Signing in in the browser itself does too: while a task waits, the service looks every 20 seconds at which sign-in forms the shared browser shows (which fields, never what is in them), and once the form on that task's site was seen and is gone, it carries on, once per blocked run. Everything is per task: the site comes from that task's own run steps (the address opened in the tab it last used, also in earlier runs of the same task), the dialog and **Open the browser** only offer that site, and a sign-in on one site never carries on a task waiting on another. When a task's site can't be told, the dialog names none and leaves it to the browser. The dialog opens the task's sign-in page itself in the shared browser, also when its tab was closed (from the address its run left off at; it never types anything there), and waits up to 15 seconds for a form. A sign-in with nothing to type (itsme or eID, a passkey, a captcha, choosing an account) shows the browser's live view right in the dialog (with `browser_vnc`; otherwise **Open the browser**), and once that task's tab is back on its site past the sign-in, the task carries on by itself and the dialog closes. **Continue** stays as a fallback. The service never starts or retries a sign-in on its own.
- **Sign in here:** next to it (and on a signed-out LinkedIn or X source in Connections), a small dialog asks for the username, password and, when the page wants one, a one-time code, and fills them into the sign-in page in the assistant's browser over DevTools (127.0.0.1 only), then submits. For a code it says which one the page wants (a text message, an authenticator app or an email, read from what the page itself says, with its sentence quoted and the number or address masked as the site masks it), offers the page's own links for another method or a new code as buttons, and shows the site's own error when a code is rejected. Only the owner on the dashboard can use it; the agent, the model, the CLI and Telegram cannot, and nothing typed there is logged or quoted in an error. It only fills the site the dialog names, on https, and empties the password field again when the page does not move on. **Save for next time** keeps that site's username and password in `browser-logins.sealed` in the data folder (mode 600), encrypted with the message key ([message protection](configuration.md#message-protection); a hosted Machine keeps that key off its disk), on this machine only. Without message protection they go in `browser-logins.enc` with a key of their own (`browser-logins.key`, mode 600), and move over to the message key once there is one; Connections, Sign-ins lists them, one row per site with its username, "Password saved" (never the password or its length) and the day it was saved, with **Forget**; when a site logs the Machine's browser out, the dialog's **Sign in as** fills them in with one tap. A move takes them along only with a passphrase. One-time codes are never saved. When the site waits on something with nothing to type after the password (LinkedIn's "approve this sign-in in your app", a two-step or check page: no form left, but the tab is still at a sign-in address), the dialog says to approve it there and keeps checking every few seconds; **Continue** checks at once, and it goes on by itself once the tab is past it. A hosted setup page opens the dialog for one site (`#signin-site=linkedin` or `x`), titled "Sign in to LinkedIn on your Machine"; once in, it says so and setup connects by itself (a LinkedIn or X connect started there waits up to 10 minutes for the sign-in). Setup says a signed-out LinkedIn or X in plain words, never the raw error code. For a captcha or anything unusual, use **Open the browser**. Anything running as the service's own user, the agent's shell included, can in principle read the key, so this keeps passwords out of the model's context, logs, support bundles and disk backups, not away from a compromised machine.
- **A browser on a server you can see:** `./install.sh --browser-viewer` gives the assistant a Chrome of its own on a virtual display (Xtigervnc), shown in noVNC through websockify at `http://127.0.0.1:6080/` (the short address sets the viewer's settings itself; the long `vnc.html?...` keeps working), with Ctrl+C / Ctrl+V (Cmd on a Mac) working between your computer and that browser. Everything listens on 127.0.0.1 only; reach it through an SSH tunnel (`ssh -L 6080:127.0.0.1:6080 server`) or your own private proxy. It starts on first use and stops after 15 idle minutes. OpenClaw gets it as its `machine` browser profile (DevTools on 127.0.0.1:9222), and the dashboard links stuck cards to it. Needs `tigervnc-standalone-server websockify novnc matchbox-window-manager` and Chrome or Chromium.
- **Your desktop's browser from anywhere:** when the assistant's browser runs on a desktop you are not sitting at, the dashboard can show that screen live in noVNC and let you use it, from your phone too. Run a VNC server for the screen that only this computer can reach, ideally on a private unix socket, and set `browser_vnc` to it. Wayland: `wayvnc --config=<file with enable_auth=false> --unix-socket <runtime dir>/vnc.sock` (a wayvnc with `--unix-socket`), with the socket in a 0700 directory, as a user service. X11: for example `x11vnc -localhost -rfbport 5905 -forever -shared` and `browser_vnc` `127.0.0.1:5905` (a 127.0.0.1 port is open to every program on this computer, a unix socket only to you). Get noVNC (your distribution's `novnc` package, or a release from its GitHub project) and build the viewer files with `python3 browser_viewer.py web ~/.local/share/machine-browser/web /path/to/novnc`. **Open the browser** then opens `https://<dashboard_host>/browser` and brings the task's tab to the front. That short address takes its viewer settings from the dashboard's own noVNC `defaults.json` and `mandatory.json` (noVNC 1.5 or later; with an older one the link is the longer `/browser/vnc.html?...`, which keeps working). On Hyprland the view opens on the browser's own window (and focuses it there), fitted to a phone's width; pinch to zoom, drag with one or two fingers to move around, tap to click, with buttons for the whole screen, zoom and the on-screen keyboard (for a password or a code). Elsewhere it opens on the whole screen. Only the dashboard's owner gets that page, and the dashboard only connects its websocket for a page on the dashboard's own address, so another site can't use your tailnet identity to reach the screen. The VNC server needs no password of its own as long as only you can open its socket; never put it on a public or tailnet address without one.
- **Signing in from a server:** X and LinkedIn often refuse sign-ins, or keep asking for checks, from data-center addresses. If The Machine runs on a cloud server, let only its browser go out through a connection at your home or office: start Chrome with `--proxy-server=socks5://127.0.0.1:1055` and point that at Tailscale's userspace SOCKS5 proxy (`tailscaled --tun=userspace-networking --socks5-server=127.0.0.1:1055`, then `tailscale up --exit-node=<your home computer>`), or at a residential proxy of your own. The rest of the server keeps its own route. Sign in once through `x.com/login`; the session stays in the browser profile.
- **Trello:** actions on the cards of one board per account (created, moved, renamed, due dates, comments, a card deleted), GET only, so the board is never marked viewed. Authorize the token with read scope only. Starts with the last seven days (`bootstrap_days`), then follows new actions with a short overlap; a long catch-up continues where it stopped.
- **RSS/Atom:** the example plugin; see [Adding a source](../docs/adding-a-source.md).

## Shortcut

The `shortcut` connector reads story pipeline transitions through GET-only search and story history. Configure the workspace slug and protected API token through `assistant connect shortcut` (inspect current help). Shortcut tokens grant broad account access, but this collector uses only reads and verifies that the token belongs to the chosen workspace. It uses the configured initial history window (default seven days), a one-day search overlap and committed pagination checkpoints; current story context may be newer than an individual transition. See `connectors/shortcut.py` and `test_connector_shortcut.py` for the exact schema/coverage. This connector was added concurrently; it is not yet a configured source in the private installation.
