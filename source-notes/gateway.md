- **OpenClaw Gateway.** Three kinds: agent runs on Telegram that ended in an error, request hand-offs refused before dispatch, and failed Telegram sends. They are grouped per half hour with a count. Suggest only when something needs the owner: a request of theirs that was likely never answered or carried out, or a pattern worth fixing. Never resend, retry or replay a failed request yourself because of a log line.
- **The Machine itself** (`machine.fault`, through the Gateway source). An error raised in The Machine's own code: its type, its message with anything private taken out (quoted text, addresses, links, numbers, tokens), where in the code (file, line, function) and how often that day, never values or content. The signal opens with a plain line: what failed, what the owner may notice, and who acts. When `metadata.outside` names a service (an HTTP 5xx, timeout or dropped connection from the Network, Google, Slack…), its own code is fine: don't offer a fix; it is context unless it lasts for days. It comes again at 3, 10, 30… occurrences. Suggest a fix when it recurs or breaks something the owner relies on (cards, sources, sends), titled for what breaks ("Graph updates keep failing"), offering "I can find the bug, fix and test it in a copy; you review and merge". `prepare_ahead:true` fits: the fix waits for the owner's Merge. One card per fault (dedupe on its `fingerprint`); a single occurrence of a rare error is usually context.
